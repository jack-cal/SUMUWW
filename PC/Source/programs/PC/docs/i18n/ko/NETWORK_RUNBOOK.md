# SUMUWW · 노드 운영

노드는 보통 발신 연결 10개를 맺고, 대부분의 연결로 블록과 거래를 중계합니다. 이미 검증한 연결을 블록 중계에 쓰거나 잠시 11번째 연결을 열어 다른 노드를 탐색할 수 있습니다. 전체 상한은 125개입니다. 수신 연결은 최대 117개이며, 발신이 10개면 최대 115개입니다. PC 화면에는 연결된 노드의 총수만 표시됩니다. 각 채굴 기기가 직접 블록을 만듭니다. PC 노드는 완성된 블록을 중계하며 휴대폰의 채굴 작업 요청과 계산 결과 제출을 거부합니다.

노드를 다시 실행하면 마지막으로 검증한 블록부터 이어서 새 블록을 확인합니다. 저장된 검증 기록이 없거나 맞지 않으면 기존 내역을 다시 검증합니다.


SUMUWW PC 0.57.61 · 노드는 체인 데이터를 검증·저장·전파·조회합니다.

## 네트워크와 주소

공개 네트워크 이름은 `sumuww`이며 `dora`는 내부 별칭입니다. 아래 제네시스 해시도 확인하세요. 기본 주소는 압축된 secp256k1 공개키의 HASH160을 사용하는 witness v0 P2WPKH입니다. 필수 메모나 태그는 없습니다. 다른 네트워크의 주소나 체크섬이 잘못된 주소는 거부합니다. HD 주소별로 수신·거스름돈 분기와 인덱스를 기록하고, 비트코인과 파생 경로가 같다고 가정하지 마세요.

## 인증과 제한

RPC를 명시적으로 켜고 숫자 루프백 `127.0.0.1:18443` 및 비공개 Bearer 토큰을 사용합니다. 지갑 잠금 해제나 원격 서명 기능은 노출하지 않습니다. 같은 PC의 서비스나 인증된 터널로 연결하세요. 브라우저의 Origin/Referer 요청은 거부됩니다. JSON-RPC는 POST `/rpc`, 객체·배열 `params`, `id`를 사용하고 알림 요청에는 HTTP 204를 반환합니다. 한도는 본문 8004096바이트, 헤더 8192바이트, 묶음 16개, 동시 요청 16개, 제한 시간 10초입니다. 페이지 limit은 1–1000, offset은 0–1000000이며 메서드 28개와 REST 경로 11개가 있습니다.

## 거래·블록 조회

`getrawtransaction`은 활성 체인과 메모리풀을 조회하며 탈락한 분기에만 있는 거래는 찾지 않습니다. 입력은 이전 출력 위치를 가리키며 단일 송신 주소를 뜻하지 않습니다. `getblock`의 `verbose`는 불리언입니다. 보관된 비활성 블록은 `active=false`, `confirmations=-1`이고 해당 블록 해시로 원시 거래를 읽을 수 있습니다. `findspendingtransaction`은 활성 체인의 확정된 사용 거래만 찾으므로 null만으로 사용 가능하다고 판단하면 안 됩니다. `include_mempool=true`인 `gettxout`도 확인하세요. 확인 횟수와 활성 여부는 체인 재편 후 달라질 수 있습니다.

## 검증

의존성을 설치한 소스에서 python examples/node_contract.py를 실행합니다. 공개 시험 키와 임시 regtest로 거래 제출·거부·확정·체인 재편·데이터 보존을 시험합니다. 실제 자금, 사용자 프로필, 하드웨어 서명기는 사용하지 않습니다.

```text
network: sumuww (dora)
genesis: 00000032e243a8c71b449b13c2da733dd329f308a75aa4358f3f22707a28af97
HRP: sumuww
P2P magic: d052470c
1 SMW = 100000000 yugeon
```

## 송금 수수료와 확인한 거래의 유지, 설치 호환성

수수료는 입력 금액 합계에서 출력 금액 합계를 뺀 값입니다. 지갑이 실제로 유효한 거스름돈을 만들 때만 견적에 거스름돈 출력의 크기를 포함합니다. 지갑의 거스름돈 기준에 못 미치는 잔액은 수수료에 합산되며, 최종 수수료와 총 출금액을 확인할 수 있습니다. 수수료율 단위는 yugeon/vB이며, 가상 크기는 거래 가중치를 4로 나눈 뒤 올림한 값입니다.

지갑은 입력과 출력을 한 번 선택한 뒤 그 거래 계획 그대로 서명합니다. 사용자가 확인하면 저장된 동일 서명 거래를 제출하며, 거래를 다시 구성하거나 수수료를 재계산하지 않습니다. 견적이 만료되거나 입력이 먼저 사용됐다면 새로 확인해야 합니다. 로컬 대기열에 접수됐다고 블록에서 확인된 것은 아닙니다.

일반 P2WPKH 송금은 low-R·low-S 서명을 사용하며 SIGHASH_ALL 바이트를 포함해 최대 71바이트입니다. 이는 지갑의 서명 생성·크기 추정 정책으로, 다른 유효 서명에 새 합의 제한을 적용하는 규칙이 아닙니다. 서명이 더 짧으면 실제 가상 크기는 추정치보다 작을 수 있습니다. 수수료율은 계속 내 노드의 대기열을 기준으로 제안하므로, 비트코인과 크기 계산 방식을 맞췄다고 비트코인 네트워크의 수수료율을 사용하는 것은 아닙니다.

## Windows I2P 구성요소와 보안 검사

Windows 배포본에는 공식 i2pd 3.0.0과 갱신한 체크섬·초기 연결용 인증서를 포함합니다. 기록된 검사에서 Defender는 공식 I2P 실행 파일과 원본 ZIP을 여전히 탐지했습니다. 공식 해시와 일치한다는 사실만으로 안전하거나 오탐이라고 확정할 수는 없습니다. 파일별 보안 예외는 등록한 PC에만 적용되며, 공개 배포본이 자동으로 등록하지 않습니다. 다른 PC에서는 같은 파일이 차단될 수 있습니다.

노드는 유효한 버전 응답을 받으면 상대 노드가 확인 응답을 보낼 시간을 따로 줍니다. 같은 노드에 두 경로로 접속한 경우에는 한 경로에서 동기화가 끝날 때까지 사용 가능한 연결을 유지합니다. 내장 자가진단은 연결 증명이 도착하기 전에 유효한 작업증명 블록을 받아들인 뒤, 연결 증명에 담긴 증인 세 명의 서명과 다른 노드로의 전파, 재시작 후 보존 여부를 확인합니다.
